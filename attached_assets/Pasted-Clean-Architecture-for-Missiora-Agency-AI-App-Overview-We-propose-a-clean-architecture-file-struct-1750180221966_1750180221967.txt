Clean Architecture for Missiora Agency AI App

Overview: We propose a clean architecture file structure for the Missiora Agency AI app to clearly separate core logic from frameworks. Following Uncle Bob’s Clean Architecture principles, business logic (like the AI agent orchestration and onboarding workflow) is isolated from UI and infrastructure details ￼. This allows focusing on the Identity → Mission → Roadmap journey and AI agent behavior without being tied to Flask, Vue, or external SDK specifics. The design is layered as follows (inner to outer layers) ￼ ￼:
	•	Layer 0 – Entities (Enterprise Business Rules): Core data models (Identity, Mission, Roadmap, etc.).
	•	Layer 1 – Use Cases (Application Business Rules): Domain logic for onboarding and agent orchestration (roadmap generation, identity analysis, session management, etc.).
	•	Layer 2 – Interface Adapters: Adapters between use cases and the outside world – e.g. Flask Controllers (HTTP routes), Presenters (formatting agent outputs for UI), and Gateways (integration to external systems like OpenAI SDK, CV module, DB).
	•	Layer 3 – Frameworks & Drivers: External frameworks and devices – the Flask app, Vue.js UI (mobile-first), camera/gesture input, database, etc. These are the outermost details that interact with the system ￼.

This structure ensures that domain-specific logic (user onboarding flow, AI agent coordination) remains independent of the web framework or UI, improving maintainability and testability ￼. Below is the final directory layout and mapping of files to each layer:

Mapping to Layers: In the above structure, directories are prefixed by layer number for clarity. Layer 0 holds plain Entities (dataclasses with minimal logic). Layer 1 contains Use Case classes and services that implement the domain-specific workflows (independent of Flask or UI) ￼. Layer 2 holds Interface Adapters – Flask route handlers (controllers), output formatters (presenters), and integration gateways for external APIs or devices ￼. Layer 3 contains actual Framework/Driver code – the Flask app instance, the Vue UI, database and hardware integrations. The dependency rule is enforced: inner layers know nothing about Flask or Vue, while outer layers depend on inner layers (never the reverse) ￼.

Layer 0 – Entities (Core Data Models)

This layer defines the core data structures for the app’s domain. Each is a simple Python @dataclass (or Pydantic model) encapsulating attributes and basic invariants, but no external dependencies or heavy logic ￼. They represent the “nouns” of the system ￼. Key entities include:
	•	Identity: Represents the user’s identity/profile. This might include name, background info, or even an avatar image reference. It’s collected in the first onboarding step. For example, Identity might have fields like name, age, profession, values etc., as provided by the user. This data class can also hold any results from analyzing the user’s photo or gestures (via CV), e.g. inferred traits (if applicable).
	•	Mission: Represents the user’s mission statement or primary goal. In the onboarding journey, after identity, the user defines their mission (what they or their brand aim to achieve). The Mission dataclass might have fields like summary (text description of the mission) and perhaps a few categorized objectives. It’s essentially the “purpose” that guides the strategy.
	•	Milestone: A granular objective or step in the roadmap. Each milestone could include a description, a category (strategy, creative, etc.), and possibly a status or timeline. For example, a milestone could be “Establish brand identity visuals” or “Launch marketing campaign”. Milestones are generated by the AI agents as part of the roadmap.
	•	Roadmap: The overall plan generated for the user, composed of multiple Milestones. The Roadmap dataclass might contain a list of Milestone objects and perhaps metadata (e.g. a title or overall summary). This is produced at the end of onboarding (after Identity and Mission are provided) by the Strategy/Creative agents working together. It essentially answers: “Given the identity and mission, what is the plan (roadmap) to accomplish that mission?”
	•	User: (Optional) Represents a registered user account (for authentication). Contains fields like id, email/username, hashed password, plus links to their saved Identity, Mission, and Roadmap (so returning users can have persistent data). Before login, a “User” isn’t created; after signup/login, the session’s data gets attached to a User record.

These entity classes reside in layer0_entities/ and do not depend on Flask, DB, or the OpenAI SDK – they are pure structures. Any business rules that belong to an entity (e.g. a method to update a milestone’s status) are kept minimal. This separation allows us to modify or extend core data definitions without affecting how they are displayed or stored ￼. For instance, we could reuse the Identity/Mission/Roadmap models in a different interface (mobile app, CLI, etc.) with no changes to their definitions.

Layer 1 – Use Cases (Business Logic & Orchestration)

Layer 1 contains the application-specific business rules – the logic that defines how the system achieves the onboarding workflow and agent interactions ￼. These are typically services or classes that orchestrate the Entities and call out to needed interfaces. They answer “how does the application fulfill the user’s goal?” Each use case is kept as independent as possible from frameworks, interacting with outside systems only through abstract interfaces (gateways). Key components in this layer:
	•	Agent Orchestrator (agent_orchestrator.py): This is the central brain coordinating all domain agents and tools. It implements the flow of agents in the app – i.e. which agent runs in what order and how they pass data ￼. Using the OpenAI Agents SDK, we define custom Agent subclasses (e.g. StrategyAgent, CreativeAgent) for different roles. The orchestrator triggers these agents in sequence or in parallel to handle the user’s input:
	•	StrategyAgent might take the Identity & Mission and produce a strategic plan or list of milestones (logical steps to achieve the mission).
	•	CreativeAgent might then take the plan or certain milestones and elaborate creative ideas (e.g. branding concepts or content suggestions).
	•	Other agents (if any, e.g. an ExecutionAgent) could handle subsequent user queries.
The orchestrator handles handoffs between agents – for example, after StrategyAgent creates a roadmap outline, it might pass each item to CreativeAgent for expansion ￼. It uses the Agents SDK to manage these workflows; the SDK provides features like multi-agent management, tool usage, and guardrails ￼. By centralizing this in one module, we ensure a single point of control for how AI agents collaborate. The orchestrator logic is pure Python (aside from calls to agent interfaces) – it doesn’t handle HTTP or UI, it just knows how to sequence agent calls and aggregate their outputs into our domain Entities. In Clean Architecture terms, this is the core interactor implementing the primary use case of the system (generating a customized roadmap via multiple AI agents).
	•	Identity Analysis (identity_analysis.py): A use-case class or function that processes the user’s Identity input. This can include validating the provided data and potentially enriching it using AI/CV tools. For example, if the user provides a profile picture or a live camera feed (with gestures), this use case would invoke the cv_gateway to analyze it. Perhaps it could infer the user’s emotional tone or style from an image, or recognize a thumbs-up gesture as a sign of confidence. This is optional, but if included, it encapsulates that logic (e.g., calling a face-recognition model or sentiment analyzer) and produces an updated Identity entity (with added attributes like persona_insights). It might also summarize the Identity to feed into the AI prompts (for instance, creating a short description of the user’s brand/persona for the StrategyAgent to use). All such processing happens here, behind an interface – e.g. this use case calls cv_gateway.analyze_identity(image) – decoupling the core logic from whichever CV library is used.
	•	Mission Service (mission_service.py): Handles the Mission step. Likely this involves taking the raw mission input (a text description of what the user wants to achieve) and performing any analysis or structuring needed. For instance, it might use an AI prompt to clarify the mission (ensuring it’s concise or goal-oriented), or simply validate that a mission was provided. It could also cross-link with Identity (e.g., check consistency or use Identity info to contextualize the mission). This use case might be simpler, possibly just storing the mission or echoing it back if no extra processing is needed. But encapsulating it here allows later expansion (like using an LLM to improve the mission statement wording, if desired).
	•	Roadmap Generation (roadmap_generator.py): This is the core use case that the app delivers – generating a tailored roadmap from the user’s Identity and Mission. Internally, this will invoke the Agent Orchestrator to actually do the heavy lifting with AI agents. For example, RoadmapGenerator.generate(identity, mission) -> roadmap would:
	1.	Call the orchestrator to initialize the agents with the context. The Identity and Mission entities are passed as context to the StrategyAgent’s prompt (e.g. “Given this user identity and mission, outline a strategy roadmap with key milestones.”).
	2.	The orchestrator runs the StrategyAgent via the OpenAI SDK (through the gateway), obtaining a draft list of milestones or strategy points ￼ ￼.
	3.	The orchestrator then might call the CreativeAgent for each milestone to enrich it (e.g. adding creative ideas or examples). The Agents SDK supports such multi-step workflows and even parallel agent runs ￼ ￼.
	4.	The orchestrator collects the results and this use case assembles them into a Roadmap entity (with Milestone objects fully detailed).
The outcome is a complete Roadmap data structure containing strategic and creative guidance. This use case abstracts how the roadmap is built. If in the future we change the agent logic (say use a single more powerful agent instead of two, or tweak the prompt strategy), we do it inside orchestrator/use-case without affecting controllers or UI.
	•	Session Manager (session_manager.py): This use case handles agent memory persistence and session-to-user transitions. The app allows an unauthenticated user to interact up to a point, so we maintain a session memory of those interactions (the “agent loop” context). SessionManager is responsible for storing and retrieving the conversation state:
	•	Pre-login (guest session): For a not-logged-in user, we might use an in-memory or server session storage to keep the chat history and the Identity/Mission/Roadmap data. For instance, when the user first arrives, SessionManager creates a temporary session ID (maybe via Flask’s session cookie). As the user provides Identity and Mission, and as the agent generates the Roadmap, all that data is cached in a session store (could be flask.session or a cache like Redis through memory_gateway). Also, each agent interaction (message from user and response from agent during the ongoing loop) is appended to this session memory.
	•	Post-login: Once the user hits the login prompt after 10 actions, the SessionManager will transfer the session data to persistent storage. Specifically, upon login or signup, this use case will create a User entity (if new) and save the current Identity, Mission, and Roadmap to the database (via the DB gateway). It will also save the conversation history if needed (could be in a Conversation table or as serialized data linked to the user). Then the session memory can either be cleared or marked as attached to that user. Going forward, any new interactions are directly logged in the DB under the user’s account.
	•	This use case also likely keeps track of the “10 meaningful actions” count. Each time the user performs a meaningful action (e.g. submits identity, submits mission, generates roadmap, or asks a question in the agent loop), we increment a counter in the session (a field in flask.session or an in-memory counter). The SessionManager (or perhaps a middleware in Layer 3) can check this count. When it reaches 10 and the user is not authenticated, it triggers the logic to prompt a login. For example, the next agent response could include a flag or message like “Please log in to continue” (possibly handled by the controller/presenter), or the controller could return a specific HTTP response that the front-end interprets as “show login modal”. We ensure this threshold logic is encapsulated so it’s easy to adjust (e.g., if we decide on 5 or 15 actions instead of 10 later, it’s one place to change).
	•	Feedback Service (feedback_service.py): A use case that handles the NPS/feedback loop. We want to capture user feedback (like an NPS rating or thumbs-up/down on responses) to improve the system. This service defines how feedback is processed:
	•	If the user provides an overall NPS score (say after using the roadmap or after a session), this use case will create a Feedback entity or simply record the score along with user/session ID and timestamp. It might call a repository via db_gateway to save it in a feedback table.
	•	If we capture per-interaction feedback (like thumbs-up/down on a particular agent answer), this could also funnel through here. For instance, the Agent UI might allow a thumbs-up on each answer; the controller will forward that to feedback_service.record_feedback(trace_id, score) where trace_id could link to a specific interaction (if using an observability tool). The service might simply log it or even trigger learning adjustments (although live training is out of scope, we can at least store it).
	•	By keeping this in a use case, we have the flexibility to either handle feedback as part of the agent loop or separately. This design leans toward treating feedback as a separate concern (not as an in-dialog agent message), which is cleaner. (We could have the agent itself ask “How was my help?” as a prompt, but that blurs responsibilities. Instead, we prefer the UI to solicit feedback and send it to this use case, so we handle it systematically.)

Each use case in Layer 1 does not depend on Flask or Vue – for example, RoadmapGenerator doesn’t know it’s being called from an HTTP request, it just takes inputs (Identity, Mission) and returns a Roadmap. This makes it straightforward to write unit tests for these behaviors without spinning up a web server. The use cases may depend on abstractions of Layer 2 (interfaces). For instance, RoadmapGenerator will depend on an interface for running the agents (OpenAI gateway) and possibly a repository interface for saving the result. Those interfaces will be implemented in outer layers. This follows the Dependency Inversion principle where the use case defines what it needs (e.g. an AgentRunner interface), and the infrastructure provides an implementation ￼.

By organizing logic this way, if tomorrow OpenAI’s API changes or we switch to a different AI backend, we only modify the gateway or orchestrator, not the core flow. Similarly, if we change how we persist sessions (say from Flask’s built-in sessions to Redis), we adjust the gateway, not the use case’s fundamental logic. The clean separation makes the system flexible and scalable ￼.

Layer 2 – Interfaces (Controllers, Presenters, Gateways)

Layer 2 contains Interface Adapters that connect the use cases to external systems and UI, adapting data as it crosses boundaries ￼. This includes:

Controllers (Flask Route Handlers)

Controllers are Flask endpoints that orchestrate the request/response flow for a given HTTP request. They belong in the Interface layer because they convert external input (HTTP, JSON) into calls to our use cases, and then package the output for the client ￼. Key controllers:
	•	OnboardingController (onboarding_controller.py): Manages the user onboarding steps (Identity → Mission → Roadmap). This could be organized as multiple endpoints or a single multi-step endpoint:
	•	POST /api/identity: called when the user submits their identity info (and possibly an image). This controller will extract the form data or JSON (e.g. name, description, maybe an image file upload) from the request. It then calls IdentityAnalysis use case (e.g. identity_analysis.process(identity_input, image)) to handle any AI/CV processing. The resulting Identity entity is saved in the session (via SessionManager). The controller then returns a success response or the processed identity data (through a presenter). The UI might then automatically proceed to the Mission step.
	•	POST /api/mission: called with the user’s mission statement. The controller calls mission_service.process(identity, mission_text) to perhaps refine or validate the mission. The Mission entity is saved (SessionManager updates session with mission). Possibly, at this point, the controller could immediately trigger roadmap generation (or the front-end might call the next endpoint).
	•	POST /api/roadmap: triggers the core generation. This controller calls roadmap_generator.generate(current_identity, current_mission). Under the hood, that uses the agent orchestrator to produce a Roadmap. This might be a longer request (several seconds if multiple agent calls). The controller could handle it synchronously (waiting for result) or asynchronously (via a background job or streaming updates). For now, assume synchronous for simplicity. Once the Roadmap entity is returned, the controller will use a Presenter to format it and send it back as JSON. It will also store the Roadmap in session (and if the user is logged in, also persist to DB via SessionManager).
The OnboardingController ensures each step’s preconditions (e.g., identity must be done before mission, etc.) possibly by checking session state. It doesn’t contain business logic itself; it delegates to use cases and manages HTTP concerns like request parsing and response formatting.
	•	AgentController (agent_controller.py): Handles the ongoing agent interaction loop after the roadmap is delivered. This corresponds to the user asking follow-up questions or executing on the roadmap with the AI’s help. For example, suppose the user, after seeing the roadmap, asks “How do I accomplish milestone 1?” via the chat interface. The front-end will send that as POST /api/agent/message (or similar). The AgentController will retrieve the current session context (Identity, Mission, Roadmap, and conversation history) via SessionManager. It will then call the Agent Orchestrator to handle the query:
	•	Possibly, the orchestrator decides which domain agent should handle the question. If the question is about a strategy detail, perhaps the StrategyAgent is invoked; if it’s about creative execution, the CreativeAgent might handle it. The orchestrator can route or even have a combined agent. In any case, the controller might call something like agent_orchestrator.handle_user_query(user_message, context) and get back the agent’s answer.
	•	The answer (agent output) is typically textual (maybe with some structured suggestions). The AgentController then passes it to the AgentOutputPresenter to format it (e.g. wrap it in a JSON with {"role":"agent","message": "..."}" so the front-end knows how to display it). It appends the Q&A to the session memory via SessionManager (so the conversation persists).
	•	It also increments the action count via SessionManager (each message exchange counts as a meaningful action). If after handling this request the count has reached 10 for an unauthed user, the controller can include a flag in the response indicating login is required next. (Alternatively, the next request could be blocked with a 401 forcing login – design choice. A user-friendly approach is to allow the 10th interaction and then respond with something like a normal answer plus a notice “Please log in to continue using the assistant.”)
The AgentController essentially acts as the API for the chat interface, continuously funneling user input to the orchestrator and returning agent outputs. This is separate from the initial roadmap generation to keep concerns clear (one is creation of the plan, the other is ongoing Q&A).
	•	AuthController (auth_controller.py): Manages user authentication (login/signup). Initially, the user is a guest (no auth). After 10 interactions, we present a login. This controller would handle routes like POST /api/login (verify credentials, create session or token) and POST /api/signup. On successful login, it calls SessionManager to merge the guest session data with the user’s account:
	•	E.g., if the user already had an Identity/Mission/Roadmap in session, after login, we call session_manager.attach_session_to_user(session_id, user_id). This will persist any unsaved data to DB and associate it with user_id. Future calls will use the DB data.
	•	The AuthController may also issue an auth token or set a secure cookie to mark the user as logged in for subsequent requests (typical Flask login flow or JWT).
	•	It might also reset the session counter since the limitation no longer applies post-login.
In clean architecture, authentication can be tricky, but essentially the controller can call a simple AuthService (could be another use-case we didn’t explicitly list) which verifies user credentials (via a User repository in DB) and returns a User entity or token. We can include that logic here or as a small use-case class. Since the question’s focus is more on the agent and onboarding, we won’t detail AuthService, but it’s understood to exist and be invoked here.
	•	FeedbackController (feedback_controller.py): Provides an endpoint to submit user feedback, like POST /api/feedback. For example, after the roadmap or at any time, the UI might send an NPS score (0-10) and maybe a short comment. Or if thumbs up/down on a specific answer, it could call this too with a payload referencing which answer. The FeedbackController will take this input and call feedback_service.record(feedback_data) in the use case layer. That service returns perhaps a confirmation. The controller can then respond with a simple success status. If needed, it could also trigger some immediate UI update (but likely just a 200 OK and the front-end will show “Thank you for your feedback”).

Controllers thus handle web/API concerns: routing, status codes, cookies/sessions, request parsing, and calling the appropriate use case. They also implement access control if needed (e.g. ensuring a user is logged in for certain endpoints – though in our scenario, all endpoints are open until the login threshold kicks in, after which the front-end will call Auth). Importantly, controllers do not execute business logic themselves; they delegate to use cases, ensuring a thin controller layer. This keeps the system modular and easier to test (business logic can be tested separately from the web layer).

Presenters (Formatting Outputs for UI)

Presenters adapt the output of use cases (which are often domain entities or raw results) into a format convenient for the view layer ￼ ￼. In a Flask+Vue context, the “view” is basically the JSON API response consumed by Vue, or the state that Vue uses. We use presenters to avoid leaking internal structures directly and to possibly embellish or sanitize outputs. Each presenter might be a simple function or class methods in our presenters/ folder:
	•	IdentityPresenter: Takes the Identity (and perhaps results of identity analysis) and formats it for the UI. For example, if the identity analysis generated some insights (say “user personality: creative”), the presenter could structure a JSON like: {"name": "Alice", "persona_insights": "creative", "profileImageUrl": "/uploads/alice.jpg"}. This way the front-end gets exactly what it needs to display in the header or profile section. It might also include an indicator if the identity step is completed successfully (for navigation state).
	•	RoadmapPresenter: Converts the Roadmap entity into a JSON or other representation the Vue app expects. Likely, the Roadmap (internally a list of Milestones) should be an array of objects with clear fields. For example:

{
  "roadmap": [
     {"title": "Milestone 1: Establish brand identity", "details": "...", "agent":"Strategy"},
     {"title": "Milestone 2: Create marketing plan", "details": "...", "agent":"Creative"},
     ...
  ]
}

The presenter might also attach metadata like the mission or identity name for reference. If any rich content was generated (say CreativeAgent returned some image URL or styled text), the presenter ensures it’s properly included or transformed to safe HTML (to avoid any malicious content). Essentially, this adapter ensures the front-end gets a tidy data structure rather than, say, a Python object or a verbose raw LLM output.

	•	AgentOutputPresenter: Formats the ongoing chat/agent responses. The agent orchestrator might return just a text answer from the LLM. This presenter can wrap it into a standardized format, for instance:

{"role": "agent", "message": "Here's how you can tackle that milestone...", "timestamp": "..."}

It could also handle special cases: if the orchestrator’s answer indicates a system event (like requiring login), the presenter might set a flag. E.g., if SessionManager noted login needed, the presenter could augment the response JSON with "login_required": true. The Vue front-end can then catch that and prompt the login modal.
Additionally, if the agent’s response includes any structured data (the Agents SDK can give structured outputs via Pydantic, for example), the presenter will convert those into user-friendly form. For instance, if an agent returns a list of suggestions as a Python list, we might turn it into a markdown bullet list string or keep it as an array in JSON for the front-end to render appropriately.

	•	FeedbackPresenter: This might be trivial – after feedback submission, perhaps we just return a simple acknowledgment message or status code. If needed, this presenter could ensure no sensitive info is returned. Or if we were to display a personalized thank-you note, it could format that.

In this design, presenters are especially useful if the internal representation differs from what the front-end expects, or if multiple front-ends (web, mobile) require different formatting. They also enforce the Dependency Rule: the inner layers provide data, and the presenters (still on the interface side) transform it for the outer layers. No inner layer code should be generating HTML or specific JSON – that’s the job of these adapters ￼. Note that since we are using a REST API with JSON, our presenters focus on JSON structuring. If this were a server-side rendered app, presenters might render templates; but here Vue will handle rendering, so we just ensure the data is clean and consumable.

Gateways (Interfaces to External Services and Systems)

Gateways in clean architecture act as bridges to external systems (tools, APIs, databases), implementing interfaces defined in the use case layer ￼. They reside in layer2_interfaces/gateways. For our app:
	•	OpenAI Gateway (openai_gateway.py): This gateway encapsulates interaction with the OpenAI Agents SDK. The use cases (especially the Agent Orchestrator) will call this gateway rather than directly calling the SDK functions. For example, the orchestrator might call OpenAIGateway.run_agent(agent, input) which internally does:
	•	Initialize the Agent (from OpenAI SDK) with specified instructions/tools (for StrategyAgent, etc.).
	•	Use the SDK’s Runner to execute the agent with the given input, maybe with observability/tracing enabled.
	•	Return the result (structured output or final answer).
By having this gateway, if the Agents SDK changes or if we switch to another LLM provider, we only change this file. It might also handle exceptions from the API (network errors, token limits) and translate them into our domain’s terms (perhaps returning an error object that the orchestrator can handle gracefully). This gateway could also include helper methods for multi-agent orchestration if needed – though largely the orchestrator logic is in Layer 1, this gateway is a thin wrapper for actual API calls.
Why a gateway for Agents SDK? Because the Agents SDK, although a library, is essentially an external dependency. Isolating it means our core logic isn’t littered with OpenAI-specific code. It also means for testing, we could mock OpenAIGateway to simulate agent responses without calling the real API. The Agents SDK offers features like tool execution and guardrails ￼; our gateway can expose those as needed (e.g., a method to register tools or to parse agent outputs).
	•	CV Gateway (cv_gateway.py): This gateway interfaces with the computer vision module. For instance, if using OpenCV or a cloud vision API to analyze images or video, this file provides functions such as analyze_identity(image) -> dict or detect_gesture(frame) -> str. The IdentityAnalysis use case calls these functions rather than embedding CV logic directly. The gateway could load a pre-trained model for gesture recognition or call an external API. By treating it as a gateway, the rest of the app doesn’t care whether we’re using, say, OpenCV vs. a custom ML model – that’s implementation detail here.
For example, if the user uses their camera during onboarding (perhaps to capture their face or a gesture indicating their mood or style), the front-end would send that image to the backend (maybe as part of POST /api/identity). The controller saves the image and calls cv_gateway.analyze_identity(image_path). In response, maybe this gateway returns something like {"dominant_color": "blue", "emotion": "confident"} or any features we want. The IdentityAnalysis use case can then incorporate those into the Identity entity (like set persona_insights = "comes across as confident"). Another use: if gestures are used for feedback (for example, a thumbs-up gesture captured via camera instead of clicking a button), the CV gateway could be used in the feedback flow to translate that into a feedback signal (this is speculative, but a neat integration given camera input).
Essentially, the CV gateway is our abstraction for any visual input processing – it could also handle something like scanning a QR or business card for identity, etc. Placing it in layer 2 keeps the CV tech separate from business logic.
	•	Memory Gateway (memory_gateway.py): An abstraction over the session store. This gateway might implement a simple interface like SessionStore with methods get(session_id, key), set(session_id, key, value), etc. Under the hood, it could use Flask’s session (which by default stores data in a secure cookie) or a server-side store. For production, we might prefer server-side (to handle more data and longer histories). We could implement MemorySessionStore that uses an in-memory cache or dictionary for quick, ephemeral storage. This is used for pre-login sessions. For post-login, the SessionManager will switch to using the DB gateway (below) to persist conversation. However, even for logged-in users, we might continue to use an in-memory cache for fast access and only occasionally sync to DB – but those are design choices beyond architecture, so we can keep it simple:
	•	If user is not logged in: memory_gateway is active (data tied to session_id).
	•	If user is logged in: memory_gateway might delegate to DB or be bypassed.
By abstracting session storage, our use cases (and orchestrator) can request to save or load conversation context without knowing if it’s coming from a cookie, Redis, or a database. This also helps in testing – we can simulate sessions easily.
	•	DB Gateway (db_gateway.py): This is where we handle persistence to the database. In Clean Architecture, typically you would define repository interfaces in the use case layer and implement them here as gateways (often called Repository Adapters). For example, we might have interfaces like UserRepository, RoadmapRepository, etc., defined in Layer 1 (or as part of Entities), and the DB gateway implements them using an ORM or direct SQL. Here, db_gateway.py could contain classes or functions for:
	•	Saving and loading Identity/Mission/Roadmap for a user (e.g., save_user_profile(user_id, Identity, Mission, Roadmap) and load_user_profile(user_id)).
	•	Storing conversation logs if needed (e.g., save_message(user_id, message)).
	•	Retrieving and storing feedback/NPS (e.g., save_feedback(user_id or session_id, score, comment)).
	•	Basic auth operations: get user by email, create new user, etc. (Alternatively, those could be separate in an auth_repository.py, but for brevity it’s under this gateway umbrella).
It could use an ORM like SQLAlchemy with classes in db/models.py for the actual schema, or even raw SQL. But the key is that these functions provide a clean interface to the rest of the app. For instance, SessionManager will call db_gateway.persist_session(session_data, user_id) on login to move session data to permanent storage, and the gateway function will handle the ORM operations (like creating a UserProfile row and Conversation entries). The use cases do not need to know anything about SQL or collections – they just call methods on an abstract repo/gateway.
In our structure, we show models.py under the frameworks layer, meaning the actual DB schema is considered part of the framework (since it’s tightly coupled to a specific DB tech, e.g., SQLAlchemy, PostgreSQL). The DB gateway in interfaces will import those models and use them to implement the repository methods. This aligns with the concept that the interface adapter transforms between the use case’s needs and the database format ￼ (e.g., converting a Roadmap entity to a set of DB rows across tables). We ensure these conversions happen at the boundary so that our entities remain plain and unaffected by database annotations or ORM cruft (some implementations might let the entity dataclasses double as ORM models – that’s possible but one must be careful to not let ORM specifics leak into core logic).

In summary, gateways enable our use cases to interact with external systems like OpenAI, computer vision, and database through a stable interface. If any of those systems change, we modify only the gateway implementation. For example, if we switch to a different LLM provider, we’d implement a new gateway (or modify OpenAIGateway) and the orchestrator use case wouldn’t need changes since it calls the gateway’s methods (like run_agent) which we keep consistent. This decoupling is at the heart of Clean Architecture’s robustness ￼.

Layer 3 – Frameworks & Drivers (Flask App, Vue UI, DB, Devices)

Layer 3 is the outermost layer with actual frameworks, libraries, and device-specific code ￼. This is where the app comes together and interacts with the real world. Key parts of this layer:
	•	Flask App (flask_app/__init__.py & config): This is where we initialize the Flask application, load configuration (like secret keys, database URL, OpenAI API keys, etc.), and register the controllers (often via Blueprints). Using Flask’s application factory pattern is common: e.g., a function create_app() that sets up the app. Here, we attach our controllers (each could be a Blueprint for a module: onboarding, agent, auth, feedback). The Flask app also sets up CORS (since Vue front-end might be on a different domain or port in dev), static file serving (maybe to serve the compiled Vue app or assets), and any middleware. For instance, we might include a middleware to count actions: every request to the AgentController could increment a counter in flask.session. However, we have SessionManager for that; still, the framework could assist by, say, adding a before_request hook to initialize session data structures if not present.
The Flask app is essentially a delivery mechanism ￼. It knows how to take an HTTP request and hand it to our controller functions (which in turn call use cases). It also knows how to serialize the response (Flask will typically JSONify dictionaries returned by controllers or use something like Marshmallow if we had). We leverage Flask’s session mechanism to store a temporary user ID or session ID for guests. Initially, each user gets a unique session cookie. We might configure the session to store data server-side if the volume is large (for example, using Redis via Flask-Session extension) – the configuration for that is defined here in Layer 3.
	•	Vue.js Frontend (vue_frontend/): The client-side interface, built as a single-page application (SPA) focusing on mobile-first design. While the front-end code is not executed on the server, it’s part of the overall architecture’s frameworks layer because it’s an external UI framework that connects to our system via the controllers. The Vue app will have components corresponding to the onboarding journey:
	•	A Header component that displays the user’s Identity info (and possibly login state). According to our alignment, the header will reflect the Identity layer: e.g., showing the user’s name or avatar (once identity is provided). It might also have a logo or app name (Missiora Agency). When the user is a guest, the header could say “Guest” or nothing; after login, it could display the username. This header stays fixed and gives context on who the plan is for.
	•	A Body area that shows the main content – which changes depending on the stage. Initially, it might show a form for Identity input (text fields, maybe an image capture widget). Next, a form for Mission input. Finally, after those, it shows the generated Roadmap (perhaps as an interactive list of milestones). During the Agent Loop, this body becomes the chat interface where the conversation with the AI agent takes place. Essentially, the body reflects outputs from the Agent/Use Case layer – the Roadmap or the agent’s answers. We ensure through presenters that the data fed into the body is easily renderable (e.g., the roadmap as a structured list, chat messages as an array of message objects).
	•	A Footer/Navigation component that provides navigation controls. This could be a simple progress indicator for the onboarding steps (Identity, Mission, Roadmap), and later maybe tabs or buttons to switch between views (for instance, “Profile/Identity”, “Mission”, “Roadmap”, “Chat”). Since the app is mobile-first, this navigation might be a bottom nav bar with icons. For example, a user can tap the Identity icon to review or edit their identity info (which might re-open the identity form, updating the Identity entity and perhaps regenerating the roadmap), tap the Roadmap icon to view the plan, or tap the Chat icon to ask a question to the agent. The navigation’s state (active/inactive) can reflect where in the journey the user is.
The Vue app communicates with the Flask backend via REST API calls (or possibly WebSockets for real-time chat, but let’s assume REST for simplicity). For instance:
	•	On Identity submission, the Vue front-end calls POST /api/identity with the data, then waits for response to proceed.
	•	On Roadmap generation, it calls POST /api/roadmap and may show a loading spinner until a response with the roadmap JSON arrives.
	•	For chat, it calls POST /api/agent/message with the user’s query and updates the chat view with the response.
	•	If a login_required flag is seen in a response (or a 401 status), the Vue app will pause interactions and show a login/signup screen/modal (which then calls POST /api/login etc.).
	•	The feedback loop might be triggered by the UI after certain events – e.g., after the roadmap is displayed, a pop-up “How helpful was this plan?” with a 0-10 scale could appear. When filled, Vue sends POST /api/feedback with that data.
Because it’s mobile-first, the design uses responsive layouts: the header might be compact, the content scrollable, and nav icons easily tappable. The architecture supports this by being stateless on the server (except for session state) – meaning each API call returns all needed info to render the next state. The state flows one way: user input → controllers/use-cases → new state output → UI. The UI can be thought of as reflecting the state of the Entities:
	•	When Identity entity is empty (not provided yet), UI shows identity input form.
	•	Once Identity is set and Mission not yet, UI shows mission form.
	•	Once Roadmap is ready, UI shows roadmap (which is basically visualization of the Roadmap entity).
	•	When in chat mode, UI is reflecting the ongoing Conversation state (which is essentially a sequence of agent/user messages maintained by SessionManager).
	•	The header can always show who the Identity is (e.g., “Plan for Alice’s Startup”) so user knows context, and the footer nav allows jumping to any of these sections if needed (depending on app flow we allow or not jumping back).
The Vue app is likely a separate project in practice, but we list it to show how it aligns with layers: it is an outer layer component that should only interact with the system via the controllers’ exposed API. It does not directly access use cases or entities; it doesn’t, for example, generate roadmap on its own – it requests it from the server. This keeps the core logic centralized and not duplicated on the client.
	•	Camera/Gesture Input (Device integration): Since the app may use camera/gestures as input (especially during Identity or for feedback), this integration happens at the framework level as well. For example, in the Vue Identity step, we might allow the user to take a selfie or do a quick video; or perhaps use a special gesture (like thumbs-up) to confirm something. The front-end would use browser APIs (getUserMedia for camera) and possibly a JS library to detect simple gestures or just capture an image frame. This captured data is then sent via the API to the backend (to the CV gateway). The heavy lifting of interpreting that image is done server-side (unless the front-end uses a TensorFlow.js model, but likely simpler to send to server).
From the architecture perspective, the camera is an external device in the frameworks layer, and our CV gateway in the interface layer is the adapter that allows the use case to get meaningful info from that device input. For instance, a user might literally give a thumbs-up in front of their camera as a feedback; the front-end could snap an image and POST it to /api/feedback with a flag gesture: "thumbs_up". The FeedbackController could then invoke CV gateway to verify that image indeed has a thumbs up, and then treat it as positive feedback. This kind of loop closes the gap between physical UI gestures and the app logic, showcasing the extendibility of the architecture.
	•	Database (DB) Implementation: The actual database (say PostgreSQL or SQLite) and its access details are part of this layer. The db/models.py might define ORM models corresponding to our entities:
	•	UserModel (table users),
	•	ProfileModel (table profiles storing Identity/Mission fields for a user),
	•	MilestoneModel and RoadmapModel (though Roadmap might just be implied by linking milestones to a user or profile),
	•	FeedbackModel,
	•	ConversationModel (to log chat messages if we want).
These models are used by db_gateway to read/write. If not using an ORM, this could be raw SQL queries in the gateway. Regardless, all specific SQLAlchemy sessions or connections are configured in the Flask app config (SQLALCHEMY_DATABASE_URI, etc.). The layer 3 could also contain migration scripts or any other infrastructure setup for the DB.
Additionally, if using a server-side session store like Redis, that is part of this layer: e.g., configured through Flask-Session. We might have a session_store.py abstraction (as listed) which internally uses Redis. But since we already have MemoryGateway, that might be enough. The main point is the concrete choices of data storage are in this outer layer. We could swap PostgreSQL for MongoDB or a flat file without touching inner layers (only the gateway and model definitions would change).

Logging & Monitoring (Framework concerns): Though not explicitly asked, typically in the frameworks layer we also set up logging (like Python’s logging config) and monitoring tools. For instance, integrating something like Langfuse or OpenTelemetry for the Agents SDK would be done here (initializing it with the app). The Agents SDK has built-in tracing; enabling it might be as simple as environment variables or slight config in our OpenAIGateway. We could use a Flask after_request to log the request and response summary for debugging. All such cross-cutting concerns live at the application setup level, ensuring they don’t clutter business logic.

Illustration of Clean Architecture layers: Entities at the core, surrounded by Use Cases, Interface Adapters (controllers, gateways, presenters), and outer Frameworks/Drivers (UI, DB, devices) ￼ ￼. This layered approach ensures each part of the app only depends on the layers inward from it, never on outer details.

Agent Memory Persistence Strategy

One of the requirements is robust agent memory persistence that transitions smoothly from guest sessions to logged-in sessions. Here’s how our architecture addresses this:
	•	Guest Session Memory: When a user first arrives unauthed, the Flask app generates a session (via a cookie). The SessionManager use case and MemoryGateway work together to maintain the conversation state. For example, memory_gateway can simply use Flask’s session object (which stores small data in a signed cookie) for lightweight info (like perhaps the Identity and Mission texts). For larger data like the Roadmap (which could be several paragraphs) or a running conversation with multiple messages, we might configure Flask-Session to use server storage (e.g. Redis or a database). In that case, the MemoryGateway could interface with that store (or we treat the server session as opaque storage that already uses Redis behind the scenes). In code, it might look like:

# Inside SessionManager or gateway
session_data = memory_gateway.get_session(session_id)
session_data['roadmap'] = roadmap  # store Roadmap (maybe serialized)
memory_gateway.save_session(session_id, session_data)

This allows the next request to retrieve the updated context. The Agents SDK may also keep some transient state (like tool usage history), but we assume each call is mostly stateless except for what we persist.

	•	Counting 10 Actions: We use either the Flask session or a custom counter in SessionManager to track actions. For instance, flask.session['action_count'] can be incremented by controllers or a before_request function. The threshold value (10) is a configuration (could be stored in config.py for easy tweaking). When the count reaches 10 and user is still not logged in, we mark a flag, e.g., flask.session['login_prompt'] = True. The AgentOutputPresenter could check this flag when preparing a response. Alternatively, the AgentController, upon seeing count == 10, could attach a special message like: “You have reached the free interaction limit. Please log in to continue.” This message can be part of the agent’s response payload (from presenter) so it’s displayed in the chat UI, possibly along with triggering the login UI.
	•	Post-Login Merge: When the user decides to log in (or create an account) after hitting the limit (or even before, if they proactively sign up), the AuthController will handle credentials and then call SessionManager’s merge functionality. This is critical: we don’t want to lose the progress the user made as a guest. SessionManager will:
	1.	Retrieve all relevant data from the guest session (Identity, Mission, Roadmap, and conversation logs).
	2.	If a new User was created (signup), ensure a User entity exists.
	3.	Save Identity, Mission, Roadmap to DB associated with that user (likely in a Profile table or similar). Possibly, mark any completed onboarding steps in the user’s record.
	4.	Save conversation history to a persistent store if we want the user to have continuity across logins (this might be optional – we could decide not to store chat history long-term for privacy, but at least the current session’s context we might want to keep until logout).
	5.	Clear the guest session or at least flag it as merged. Possibly regenerate the session cookie for security (Flask does this on login by default to prevent session fixation).
	6.	Set the user as logged in (e.g., using Flask-Login or setting a user_id in session).
After this, when the user continues, the controllers will detect an authenticated user and use the DB-backed storage. For example, AgentController when fetching context will see user_id, and use DBGateway to load Identity/Mission/Roadmap instead of memory. We ensure the orchestrator still gets the same data, just from a different source.
	•	Persistent User Sessions: For subsequent visits (user coming back later logged in), the system can load their last saved state. E.g., if they log in on a new device, load_user_profile can fetch their Identity, Mission, Roadmap so far. We might or might not load past conversation (maybe not, to start fresh). But at least their roadmap can be displayed from DB. This means our architecture supports continuation: once trained via interaction, the agent could pick up where the user left off if desired, since Identity and Mission are stored, and possibly key feedback or adjustments (one could imagine storing which answers the user liked vs disliked to tailor future responses – though that’s advanced).

By designing SessionManager and gateways this way, the user’s journey from anonymous to authenticated is smooth and data-complete. It also respects Clean Architecture: the SessionManager and use cases don’t care how the session is stored (cookie vs DB), they just call the appropriate gateway. The controllers don’t implement merging logic, they just invoke SessionManager, maintaining separation of concerns.

NPS Feedback Loop and Logging Strategy

Feedback Loop (NPS & Quality): We incorporate a feedback mechanism to continuously improve the agent. As discussed, it’s implemented via FeedbackController and FeedbackService use case. Here are recommendations on how to best handle it:
	•	Treat feedback gathering as a separate concern from the core agent conversation. This means using a dedicated UI element (like an NPS popup or thumbs buttons) rather than relying on the AI agent to ask for feedback. This is more reliable for data collection. The front-end can prompt the user after significant milestones: e.g., right after the roadmap is displayed, ask “On a scale of 0-10, how helpful is this plan?” or after a chat session, ask for a thumbs-up/down on the last answer.
	•	The feedback submissions are sent to the backend and handled by the FeedbackService. We store feedback in a Feedback table with fields: user (or session id if guest), score, comment (optional), context (maybe which feature or which agent response it pertains to), and timestamp.
	•	This data can be periodically analyzed by developers or even an admin interface. It’s useful to identify if the average NPS is low in certain areas, indicating the need for improvement. Because the feedback is linked to either a user or at least a session, we can also see if first-time users have different feedback than returning users.

Should the agent itself incorporate feedback at runtime? Possibly in the future, but initially we recommend not to automatically retrain or alter the agent behavior based on one user’s feedback in real-time (that’s complex and risks instability). Instead, use the collected feedback offline to refine prompts or model choices. For example, if many users give a thumbs-down to the creative suggestions, we might adjust the CreativeAgent’s prompt to be more concrete, or switch to a different model.

There is also an idea of the agent getting immediate feedback in context – e.g., if a user thumbs-down an answer, the orchestrator could choose to have the agent apologize or try a different approach. This would involve feeding that signal into the use case: the FeedbackController could inform the orchestrator or store a flag accessible by AgentController that the last answer was disliked, and maybe the orchestrator can escalate (for instance, switch to a different agent or re-run with a different strategy). This is an advanced behavior and can be added without breaking structure (just another branch in orchestrator logic reading from a feedback store). Initially, we likely keep it simple: feedback is logged, not immediately altering the single session’s agent (aside from the user potentially re-asking or clarifying).

To directly address the question: Where to store the feedback loop? We choose to implement it as its own interface component (controller & use case) rather than embedding in the agent. This keeps feedback handling decoupled. The agent’s job is to provide help; the feedback system’s job is to evaluate that help. By separation, our agents remain unaware of feedback (they don’t alter their behavior mid-session trying to game feedback), and the feedback logic can evolve independently (like adding different types of surveys).

Logging and Agent Monitoring: For an AI-driven app, logging is crucial. We have several layers at which to log:
	•	Application Logs: We should log important events in the Flask app (Layer 3) – for example, when a roadmap is generated or when an error occurs. Python’s logging module can be configured to output to console or file. Each controller can log a summary of what happened (e.g., “Roadmap generated with 5 milestones for user X” or “StrategyAgent took 8 seconds, tokens used 1200”).
	•	Agent Execution Logs: The OpenAI Agents SDK provides tracing and observability features ￼. We should leverage these. For instance, the SDK can output a step-by-step trace of agent actions (calls to tools, LLM calls, etc.). We might integrate an observability tool like Langfuse or use OpenAI’s built-in tracing UI:
	•	Using Langfuse or similar, we can capture each agent run, the tools it used, and the outputs. This creates a rich log that can be inspected after the fact. As an example, we can attach user identifiers or session IDs to these traces ￼ ￼. This way, if a user reports a bad response, we can find the exact trace of what the agent did.
	•	We also incorporate user feedback into the traces, if possible. For example, if a user gives a thumbs down to an answer, we can log that alongside the trace of that answer ￼ ￼. This ties qualitative feedback to the quantitative trace. Over time, this helps pinpoint patterns (e.g., “When the StrategyAgent uses ToolX, users often give low ratings”).
	•	The Agents SDK tracing can often be enabled by environment variables or minimal code. We can run the orchestrator calls within a tracing context (as in Langfuse’s example, they use a context manager start_as_current_span to log an agent’s run ￼). We should do similar in our OpenAIGateway: wrap Runner.run(agent, input) in whatever tracing hooks are needed.
	•	Content Logs: We may want to log the actual conversations (questions and answers). This is sensitive data, so it should be stored securely (possibly encrypted if containing personal info). Logging complete dialogues helps in fine-tuning and debugging. For instance, if a user’s roadmap was totally off-base, we could review the Identity, Mission, and agent outputs to see what went wrong (maybe the prompt misunderstood the mission).
	•	We could store dialogues in a conversations table or simply log to a file. Given potential volume, a database table with an index by user or session might be better for querying specific sessions.
	•	We can also implement a retention policy (e.g., delete or anonymize guest conversation logs after X days if the user never signs up, to respect privacy).
	•	Performance Metrics: Monitoring token usage, response time, etc., is also part of logging strategy. The Agents SDK might give token counts. We can log how many tokens each agent call used, and how long each call took. Over time, this data is useful to optimize costs and speed (for example, if CreativeAgent is too slow, maybe use a smaller model for it).
	•	The orchestrator could gather such metrics (with help of the OpenAI gateway, which might return token usage info) and then log it via Python logging or send to an analytics dashboard.

Agent Feedback in Development: We can incorporate a practice where developers regularly review logs and feedback to adjust the system. Perhaps run weekly sessions where the team looks at the NPS scores and a few random conversation logs to glean insights.

One interesting advanced approach is automated evaluation – e.g., using an LLM to rate the agent’s output (as mentioned in Langfuse docs) ￼. While not asked, our architecture could allow an evaluation agent as another domain agent. But that might be overkill here; instead, a simpler check could be done in the presenter (like if the agent’s response seems off, flagged by some heuristic). However, this is beyond scope unless needed.

In short, our logging strategy is:
	•	Use the Agents SDK’s built-in tracing & observability to log agent steps and tool usage ￼.
	•	Record user feedback alongside these logs to correlate human ratings with agent behavior ￼.
	•	Log high-level events and errors in the backend for debugging.
	•	Store key interaction data in a database for analysis (with user consent as appropriate).
	•	Keep feedback data in a structured form so we can compute metrics like average NPS, or track changes after updates.

By following these practices, we ensure a feedback loop that not only captures user sentiment (NPS) but also provides the developers concrete data to iterate on the agent’s performance ￼ ￼. This closes the loop of training via interaction: the agent’s knowledge itself might not update automatically, but the developers (or a training pipeline) use the feedback and logs to make continuous improvements, which ultimately results in a better experience for users.

Aligning Visual UI Flow with the Architecture

Finally, we map the UI components to our architecture to ensure the design is cohesive:
	•	Header = Identity: The app’s header displays information about the user’s identity and status. This corresponds to data from the Identity entity (Layer 0). Through the layers: the IdentityPresenter ensures the Vue header gets necessary info (e.g., user’s name or a greeting). When the user updates their identity (say they change their name or upload a new picture), the front-end calls the identity route, which updates the Identity entity and then the presenter returns updated info to refresh the header. The header might also show a login button or user icon – tied to Auth state. That state is managed by AuthController and stored in session/User entity. The architecture cleanly separates this: the header component doesn’t manage identity logic, it just displays what the controllers/use-cases supply. So identity changes propagate from Entities to UI via the interface layer.
	•	Body = Agent (Main Content): The body of the UI is primarily driven by the Agent Orchestrator outputs, which are results of use cases (Layer 1). In the onboarding phase, the body shows forms or results:
	•	During Identity and Mission input, the body is effectively showing input forms, which are part of the UI but the submission of those forms goes to controllers as described. Once submitted, any analysis (like CV results) returned by the IdentityPresenter could also be shown (for example, after uploading a photo, the app might display “We see that your brand color could be blue based on your image” – this text would come from identity_analysis via presenter).
	•	When the Roadmap is generated, the body shows the roadmap content. This content comes from the RoadmapPresenter in a structured format. The Vue component will iterate over milestones and display them nicely (maybe with icons representing strategy vs creative tasks, etc.). So the body at this stage reflects the Roadmap entity. If the user navigates away and back, the front-end can call an API to fetch the roadmap (or keep it in memory if it’s a SPA), which would again come from the RoadmapPresenter (pulling from session or DB).
	•	In the agent chat phase, the body is a chat interface. The messages displayed are results of the AgentController calling the orchestrator. With each user message:
	•	The UI appends the user’s message to the chat view (optimistically perhaps).
	•	Then it waits for the response from backend. The AgentOutputPresenter gives the response content, which the UI then appends as the agent’s message bubble. This back-and-forth continues, and all of it is grounded in the orchestrator use case’s functioning. The UI doesn’t contain the logic for answering – it’s just rendering messages from the agent.
	•	Because of our design, the agent’s responses can include structured suggestions (like “here are 3 options I suggest”). If so, the presenter can format that into, say, a list that the UI knows how to display (maybe as clickable options or just as text bullets).
	•	If the user’s question triggers a tool (e.g., a web search, if such a tool existed), the orchestrator might provide an interim message like “Searching for X…”. The UI can handle streaming or intermediate messages if we design it (that would involve more complex real-time updates, perhaps via WebSocket or server-sent events – not detailed here, but the architecture could support it by having the orchestrator yield partial results).
	•	Thus, the body UI is essentially a view onto the outputs of our domain use cases: whether that’s the generated roadmap or the ongoing agent advice. Changes in business logic (like adding a new type of milestone or a new agent capability) will reflect in what’s presented, but the way it’s presented can be adjusted in the presenter or front-end without altering the core logic.
	•	Footer = Navigation: The footer nav is a UI element to navigate different parts of the app (Identity, Mission, Roadmap, Chat, etc.). Clicking these will likely:
	•	Update the front-end route/state (if using Vue Router, different routes or components).
	•	Possibly call some API if data needs refreshing or action needs triggering. For example, if a user goes back to the Identity section to edit it, the front-end might show the Identity form pre-filled with current values (which it could get from an API call to, say, GET /api/identity returning the Identity entity data).
	•	The navigation’s logic (what sections are available, when) is determined by the application state. E.g., before Identity is submitted, maybe Mission and Roadmap sections are disabled. After a roadmap exists, all three might be accessible for review or edits. This state logic can be derived from the presence of data in the session (via an endpoint or by including flags in responses).
	•	Each nav item corresponds loosely to a controller’s domain:
	•	Identity nav -> shows Identity UI (likely no new API call if already loaded, or maybe a refresh from session data).
	•	Mission nav -> Mission UI.
	•	Roadmap nav -> Roadmap view (which could call a GET /api/roadmap that triggers RoadmapPresenter to fetch current roadmap from session/DB).
	•	Chat nav (if separate from roadmap) -> Chat interface (could call an endpoint to fetch recent conversation if we want to display history).
	•	Possibly a Profile/Settings nav for logged-in users to manage account (this would be tied to AuthController).
	•	The navigation interacts with controllers mostly via read operations (once data is there). If user goes back and edits Identity, that would be a new POST to IdentityController and then presumably regenerate the roadmap (maybe we’d call roadmap generation again or prompt user to regenerate).
Importantly, the footer nav is just triggering actions or views; the actual consequences (like regenerating a roadmap if identity changed) are handled by our controllers and use cases. The UI flow is thus synced with the use case flow:
	•	You can think of Identity, Mission, Roadmap, Agent Loop as states in a state machine. The nav allows moving between some of those states (with some guarded transitions). The rules of those transitions (e.g., “if Identity changes, Roadmap should be refreshed”) are enforced by the backend (the backend knows to recompute roadmap if identity is updated, or at least marks it stale). The front-end just provides the means to initiate that.

Finally, the architecture ensures that no matter how the UI evolves (say we redesign the navigation or add a new step), the core layers are unaffected. If we wanted to A/B test a different onboarding sequence (like asking Mission first then Identity), we could tweak the front-end and maybe adjust controllers, but Entities (Identity, Mission) and use cases (analysis, generation) remain valid – just called in a different order. The clean separation of concerns makes such changes feasible with minimal risk of breaking unrelated parts.

⸻

In conclusion, this clean architecture filesystem design provides a scalable foundation for the Missiora Agency AI app. By dividing the project into Entities, Use Cases, Interfaces, and Frameworks ￼ ￼, we achieve: a clear structure where the AI agent orchestration logic (OpenAI Agents SDK usage) lives in the core, the onboarding workflow is encapsulated in testable use cases, and the Flask+Vue specifics are confined to the outer layers. The agent’s memory is persisted seamlessly from session to database, and a feedback loop is in place to continually refine the user experience. The UI flow (header/body/footer) is naturally supported by this architecture, as the data each UI element needs is provided by the corresponding layer (identity in header, agent output in body, navigation triggering controllers). This alignment ensures that as the agent is trained via interaction and user state flows through Identity → Mission → Roadmap → Agent Loop, the system remains organized and maintainable. Each layer can be modified or replaced (e.g., swapping Vue for React, or OpenAI for another AI engine) with minimal impact on the others, fulfilling the promise of Clean Architecture: focus on business logic while being adaptable to technology changes ￼.
