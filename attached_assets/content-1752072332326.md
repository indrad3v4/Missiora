Digital wallet system is used by client to store money in the wallet and spend it later.

For example, you can add money to your digital wallet from your bank card and when you buy product online you can given the option to pay using the money in the wallet.

![](https://miro.medium.com/v2/resize:fit:700/1*zdjgwivDw_y-EqNpPCKjWw.png)

Other than spending money, user can also directly transfer money to somebody else’s wallet on the same payment platform.

![](https://miro.medium.com/v2/resize:fit:700/1*5t1oxfTSqZwxhUWnpmzcsg.png)

Compare to bank to bank transfer, direct transfer between digital wallets is faster and most importantly it usually does not change an extra fee.

Let’s design a Digital wallet system to support 1 million transaction per second.

# High level system design

At the core, Wallet service should support transfer command i.e. to transfer amount `$x` from account `A` to account `B` . Following is wallet service high level system design.

![](https://miro.medium.com/v2/resize:fit:700/1*Fne8KK7Q-cYpQmvMtVJW8A.png)

Each transaction for example `A-$1 ->B` split into two transaction

1. `A-$1`
2. `B+$1`

To support scale, we need to support distributed transaction across the different shard.

Spanner database is very beautifully support transaction and strong read across the different shards therefore very much suitable for this application.

# Event sourcing

In real life, a digital wallet provider may be audited. These external auditor may ask for following

1. Do we know the account balance at any given time.
2. How do we know the historical and current account balances are correct?
3. How do we prove that the system logic is correct after a code change.

We can use Event sourcing design design pattern to answer these questions.

## Event sourcing terminologies

There are foud important terms in the event sourcing

1. Command
2. Event
3. State
4. State machine

## Event sourcing on Wallet service

For wallet service, the commands are balance transfer requests. These commands when written into Spanner storage, can read the previous command to establish the order.

```
Command  Timestamp  PrevTimestamp
A-$1->B  T1         Null
A-$5->B  T2         T1
B-$1->C  T3         T2
```

The state machine examine each command one by one based on order. For each command, it checks weather the account has a sufficient balance. If yes, then state machine generates an event for each account.

For example `A-$1->B` will generate `A-$1` and `B+$1` event.

# Reproducibility

All wallet changes are saved first as immutable history. We can always reconstruct historical balance states by replaying the events from the very beginning.

# Command query responsibility segregation

So far we have designed wallet system to move money from one account to another efficiently. However client still does not know what the account balance is.

There needs to be a way to publish state so the client which is outside of the event sourcing framework can know what the state is.

Rather than publishing the state (balance information), event sourcing publishes all the events. These external world would could rebuild any customized state itself. This design philosophy is called CQRS.

In CQRS, there is one state machine responsible for the write part of the state, but there there can be many read-only sate machine which is responsible for building view of the state. These views could be used for queries.
